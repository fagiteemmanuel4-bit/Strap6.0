# React migration — preserve existing Strap UI

## Scope and safety rules

- Work only in `fagiteemmanuel4-bit/Strap6.0`.
- Preserve the existing visual design, CSS tokens, spacing, typography, responsive behaviour, copy, and interaction patterns. React migration is not a redesign.
- Keep Neon Auth, Neon/Postgres, Vercel API handlers, MCP protocol, storefront API, SQL migrations, and public storefront URLs unchanged.
- Keep the migration on `migration/react-preserve-design` until the React build, existing tests, and production-like route checks pass.

## Baseline architecture found

The app currently uses classic browser scripts and global modules (`StrapAPI`, `StrapStore`, `StrapProducts`, `StrapSales`, `StrapSettings`, `StrapFeatures`, `StrapPages`) that render and update DOM nodes directly. The dashboard's script load order is significant. Public storefront HTML is generated by the API and loads `storefront.css` and `storefront-client.js` directly. Several standalone HTML routes must remain available.

## Migration sequence

1. **React/Vite foundation (this branch):** introduce React 19 and a multi-page Vite build. React owns the runtime entry points; existing screens and styles remain intact behind a temporary compatibility bridge. Keep static pages and server-generated storefront assets in the output.
2. **Shared primitives:** port existing UI helpers, modal/sheet, picker, toast, and navigation into React components while matching the existing DOM structure and CSS classes. Add component-level interaction tests.
3. **Feature pages:** migrate dashboard, products, sales, orders, inventory, customers, online store, MCP, settings, and other page modules in small groups. Keep existing `StrapAPI` contracts and persisted data formats during each step.
4. **Authentication:** migrate sign-in, sign-up, verification, password reset, and onboarding only after auth regression tests cover all existing flows.
5. **Retire compatibility bridge:** remove classic scripts only after equivalent React screens and regression tests are complete.

## Acceptance gates

- Existing route URLs and storefront URLs resolve exactly as before.
- No schema, migration, RLS, RPC, or backend behaviour changes as part of the UI migration.
- Existing CSS files remain the source of truth until parity is verified; no redesign or blanket CSS changes.
- Existing test suite and syntax checks pass; add tests for each migrated feature.
- Preview deployment is checked before merging. Production is not switched until the full migration is complete and verified.

## Current status

Phase 1 introduces the React/Vite runtime entry points and keeps the existing DOM-driven screens running as a compatibility layer. This is intentionally not presented as a completed React rewrite; feature modules must be migrated in subsequent phases.
